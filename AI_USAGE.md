# AI Usage

This document was updated as the project progressed, not written retroactively at the end — the point is to capture what actually happened, including mistakes, as they happened.

## Tools used

- **Claude (Anthropic), via Claude Code**

## Representative prompts

**1. "Interview me relentlessly about every aspect of this plan until we reach a shared understanding. Walk down each branch of the design tree, resolving dependencies between decisions one-by-one. For each question, provide your recommended answer."** This produced a structured back-and-forth covering datastore choice, concurrency strategy, idempotency storage, daily-limit computation, audit log design, JWT mock scope, wallet cardinality, and error-response shape — each with a recommendation and trade-off. Several of the AI's first-pass instincts got pushed back on and changed as a result (see "Caught mistakes" below).

**2. "Before I sign off on the money-movement code, I want to verify every credit in this system has a corresponding debit — go through each write path and show me the matching leg."** Requested during a file-by-file review of the finished transfer/credit code, this systematic check exposed that `WalletCreditService` — the simulated inbound NIP endpoint — wrote a single, uncountered `Credit` row, effectively materializing money from nothing. Full write-up under "Missing double-entry leg on simulated inbound credits" below.

**3. "What if a transfer is between two accounts that already exist in this ledger — did we factor that in?"** The most serious thing this review turned up: nothing stopped the settlement account from being named as either side of an ordinary `POST /transfers` call, which combined with its negative-balance allowance was an unlimited money-creation path. Full write-up under "Unlimited money-creation path through the settlement account" below.

**4. "What happens if the outbox dispatcher is ever scaled to more than one pod/replica? Does one pod's poll double up on work another pod already picked up?"** The honest answer was yes — nothing in `DispatchPendingAsync` prevented a second replica from double-processing the same batch. Full write-up under "Dormant multi-pod race in the outbox dispatcher" below.

**5. "I want to walk through what happens at real operational scale, not just the happy path. Idempotency keys get written on every transfer and are never cleaned up — won't that table get bloated, and should there be archiving or deletion after some period?"** Raised during a pass specifically checking for unbounded-growth and operational-scale gaps, this surfaced a real, previously unflagged issue — `idempotency_keys` had no retention policy at all. Reasoned through with the AI and deliberately documented rather than built; see "`idempotency_keys` has no retention policy" below.

## Caught mistakes — where the AI's output was wrong or naive for a financial system

### Money-safety bugs

These are the ones that actually touch correctness of money movement — the category the brief is really asking about.

**1. A real concurrency bug in the transfer's row-locking code (the most serious one).** The AI's first implementation of `TransferService.LockWalletAsync` locked both wallet rows using EF Core's `db.Wallets.FromSqlInterpolated("SELECT * FROM wallets WHERE wallet_id = {id} FOR UPDATE").ToListAsync()`. Syntactically valid, a commonly-recommended pattern, and it passed casual manual testing (single requests worked fine).

Under real concurrent load it silently broke: the **second** of two sequential `FOR UPDATE` locks taken within the same transaction sometimes returned a stale, pre-commit balance instead of the value the concurrent transaction had just committed. In a controlled reproduction (two simultaneous transfers draining the same ₦100 wallet), both transfers read the original balance, both computed "sufficient funds," and both committed — a genuine double-spend, ₦200 moved out of a ₦100 wallet. Critically, **every individual HTTP response was well-formed and plausible** (`201 Created`, correct-looking JSON) — nothing about a single request's response revealed the corruption. I only caught it because the automated concurrency test asserts the *exact* success count and *exact* final balances across a burst of concurrent requests, not just "did each request return without error."

Diagnosed by adding timestamped instrumentation around each lock acquisition and commit, which showed the second lock's `SELECT ... FOR UPDATE` returning data from before the first transaction's commit even though it started well after that commit completed. Fixed by pulling the locking read out of EF Core's tracked-entity query pipeline (`FromSqlInterpolated` against `DbSet<Wallet>`) and reading the row through a plain `DbCommand`/`DbDataReader` on the transaction's own connection instead, reconstructing the `Wallet` domain object from raw columns. Verified with repeated 20-request concurrent bursts against both the Testcontainers suite and a live `docker compose` stack.

This is exactly the class of bug the brief calls out — a locking bug that looks correct in isolation, produces plausible-looking output per request, and only manifests as data corruption under real concurrent load. Without a concurrency test asserting aggregate correctness (not just per-request status codes), this would have shipped.

**2. A missing double-entry leg on simulated inbound credits.** `TransferService` *is* properly double-entry (every transfer writes a `Debit` and a `Credit` against each other), but `WalletCreditService` — the simulated inbound NIP endpoint — was writing a single, uncountered `Credit` row. Money was materializing from nothing rather than being debited from anywhere, and the AI hadn't flagged this as a limitation on its own. Fixed by introducing a fixed, non-customer-facing settlement account (`WellKnownWalletIds.NgnSettlementAccount`, seeded by migration, `AllowsNegativeBalance = true` since it represents a liability to the outside world rather than actual funds) that every credit now debits as its matching leg, reusing the same ascending-`wallet_id` locking discipline as transfers. The code satisfied every existing test and every explicit acceptance criterion, but violated a domain principle (every credit needs a matching debit) that nothing in the suite was asserting, because no test had been written to check for it.

**3. An unlimited money-creation path through the settlement account.** `TransferService` correctly never touches the settlement account for an ordinary customer-to-customer transfer, but nothing stopped the settlement account from *being* one of the two wallets in an ordinary `POST /transfers` call — it's just another `wallets` row as far as `TransferService` is concerned. That matters because the settlement account allows a negative balance, and `Wallet.Debit()` skips the insufficient-funds check entirely for that flag. Two independent paths to the same bug:

- **Reachable by any authenticated customer:** `ToWalletId` on a transfer requires no ownership check, only `FromWalletId` does — any customer could set `ToWalletId` to the settlement account's fixed GUID.
- **Reachable via the mock auth issuer:** `POST /auth/token` mints a JWT for *any* `customerId` string with zero identity verification, including the settlement account's own `CustomerId`. That token would pass the ownership check on `FromWalletId`, letting a caller repeatedly debit the settlement account (which never runs out, since it's allowed to go negative) into a wallet they control — an unlimited money-creation loop bypassing the one intended door (`WalletCreditService`).

Fixed at two layers, deliberately not just one: `TransferService.TransferAsync` now rejects the settlement account as either side of a transfer outright (checked before any lock is taken — this is the real fix, since it holds regardless of how a caller got a valid-looking identity for it), and `AuthEndpoints` separately refuses to mint a token for the reserved `customerId` at all. This was found by continuing to interrogate a design that had already been through two rounds of review without catching it — "we already reviewed this" isn't the same as "there's nothing left to find."

**4. A daily-limit bypass between `internal-transfers` and `external-outbound`.** `TransferService`'s daily outbound limit query sums every `Debit` for a wallet regardless of counterparty, but `OutboundService.DebitAsync` didn't call it at all in the AI's first pass — meaning a customer could spend up to the daily cap via `internal-transfers`, then spend up to the same cap *again* via `external-outbound`. Caught by re-reading `TransferService`'s existing daily-limit code while reviewing its sibling, not by a test (none existed yet, since the endpoint was new). Fixed by adding the identical query/check to `OutboundService.DebitAsync`, run while still holding the wallet's row lock, and covered by a new test that spends part of the limit through one endpoint and proves the other respects the remaining headroom.

**5. A dormant multi-pod race in the outbox dispatcher.** The outbox dispatcher runs as a `BackgroundService` polling every 5 seconds inside the API process. Nothing in `DispatchPendingAsync` prevented a second replica from double-processing: it read the pending batch with a plain EF LINQ query — no `FOR UPDATE`, no claim step — and only marked rows dispatched *after* `Publish()` had already run for each one. Harmless today since `docker-compose.yml` runs exactly one API instance, but it was never actually designed for more than one — the assumption was implicit in using an in-process `BackgroundService` at all, and nothing flagged it as a scaling limit. Fixed the same session it was raised: `DispatchPendingAsync` now opens an explicit transaction and reads its batch via a raw `SELECT ... FOR UPDATE SKIP LOCKED`, the same locked-read discipline `WalletLock.cs` already uses for wallet rows. Verified with a new test that fires four concurrent `DispatchPendingAsync()` calls from four independent DI scopes (simulating four pod replicas) and asserts the *sum* of their dispatch counts is exactly 100, not more. A question about operational reality — what happens at more than one replica — that the AI's own design never had reason to ask itself; a single-process background poller "just works" until it's run more than once.

### Design decisions corrected before any code was written

**1. Storing the daily-spend limit as a maintained counter.** During the design interview, the AI's first-pass recommendation for the daily outbound transfer limit was a running `daily_spent` counter per wallet, reset by a scheduled job at midnight — a reasonable pattern in general, but wrong here. It introduces a second source of truth that must stay consistent with the ledger's actual transaction history, needs a scheduled job to reset correctly at a timezone boundary (WAT, not UTC), and would silently drift from the truth if that job ever failed or double-ran. I pushed back and had it justify the counter approach against the simpler alternative; the corrected design — computing the daily total by querying the transaction table directly, with the WAT boundary computed at query time — has no reset job and no second copy of the truth, which is strictly more correct for a ledger where "the transaction table is the truth" is meant to be a hard invariant.

**2. Modeling a wallet as one-per-customer, keyed directly on `customer_id`.** The AI's first-pass wallet schema keyed `wallets` directly on `customer_id` — effectively `UNIQUE(customer_id)`, one wallet per customer. It's the obvious shape for one NGN savings wallet per person, and it would have passed every acceptance criterion. I steered it off this specifically to support additional wallet types later without redesigning the transfer/audit primitives — a `UNIQUE(customer_id)` key can't do that; the day a customer needs a second account, either uniqueness breaks or the schema needs a live migration. The corrected shape, adopted before any code existed: `wallets` gets its own surrogate `wallet_id` primary key decoupled from `customer_id`, with `UNIQUE(customer_id, currency, account_type)` defaulting to `SAVINGS`. Every other table references `wallet_id`, never `customer_id` directly, so a customer gaining a second wallet type later is just a new row. The "obviously correct" schema for the literal acceptance criteria in front of you can still be the wrong one once you account for where the system is actually meant to grow — and that's a distinction I had to name out loud, not one the AI inferred unprompted.

### Gaps found by review and hands-on testing

Lower-stakes than the two tiers above — mostly naming, API surface, and operational polish — but still worth recording as part of how this got built.

**UUIDv7 for every PK.** Not a mistake, a trade-off interview: I pushed on GUID-vs-`bigint` for insert performance at scale, and `Guid.NewGuid()` (fully random UUIDv4) was replaced with a time-ordered UUIDv7 at all four ID-generation sites, fixing random-insert index fragmentation while keeping client-side generation. Required zero schema change — only how the value is generated.

**A customer-facing account number, separate from `wallet_id`.** I pointed out customers can't be expected to type a GUID. Added a random 10-digit `account_number`, unique via a DB constraint, resolved back to a wallet through a new lookup endpoint — `wallet_id` stays the only thing any FK, lock, or internal path references. One deliberate gap: a collision-retry path exists (bounded at 5 attempts) but isn't covered by a test, since forcing a real collision deterministically would need test-only RNG scaffolding disproportionate to how improbable it is.

**A missing "list my wallets" endpoint, found by hands-on Swagger testing, not a design conversation.** `wallet_id` was only ever observable from `POST /wallets`'s own creation response — there was no way to ask "what wallets do I own?" afterward. Caught by actually poking at the running stack, not a design review, since every existing test always captured the ID at creation time and never needed to look it up again. Fixed with `GET /wallets`, filtered by the JWT's `customer_id`. Same pass also caught that Swagger showed every endpoint as one flat, ungrouped list — a Minimal API vs. controllers trade-off nothing had actually applied (`.WithTags(...)`) — fixed by tagging every endpoint group.

**Renaming the money-movement endpoints, which surfaced a missing reversal leg.** A naming review (`GetWalletBalance` actually returning the full wallet; `POST /transfers` and the credits route not reading as the same "money movement" concern) led to `internal-transfers` / `external-inbound` / `external-outbound` as three distinct routes rather than one generic "create transaction" endpoint — rejected because the three diverge on caller identity, ownership checks, and request guarantees (idempotency key, rate limiting) in ways that would otherwise collapse into conditional logic inside one handler. Working through that distinction surfaced a genuine gap: `external-outbound` didn't exist anywhere yet, and building it required a **reversal leg** — an outbound NIP debit commits its internal leg before knowing whether the receiving bank actually accepts the funds, so a later rejection needs a correction insert, never an update/delete, consistent with the append-only audit model already in place.

**Building the reversal leg itself.** Went through a few rounds before landing right: the first idea was a `pending`/`settled`/`reversed` status lifecycle for the debit, corrected because the debit itself is real and final the instant it commits — only the *correction* is uncertain, which is a smaller thing to track than a status enum. The first schema idea put `reversal_of_transaction_id` directly on `transactions`, reconsidered because that's the single hottest table in the system and this project already isolates rare concerns into their own small tables — landed on a dedicated `transaction_reversals` table with `original_transaction_id` as the primary key, so a second reversal attempt hits a PK violation rather than relying on an application-level check-then-act race. Verified by a concurrency test firing ten simultaneous reversal calls against the same transaction and asserting exactly one succeeds.

**A gateway/orchestration layer as the reason this ledger stays narrow.** Not a mistake — a retroactive justification for a decision already made. This ledger's API should never be called directly by a client app in a real deployment; a gateway layer in front of it should own real authentication and classifying what kind of movement a request represents, calling into this ledger's posting operations only once a request is already classified. Recorded in the README under "Out of scope" rather than left as a passing remark.

**Splitting the single settlement account into separate inbound and outbound accounts — my suggestion, not something the AI surfaced.** While walking through `Wallet.AllowsNegativeBalance`, I raised that real settlement/nostro accounts commonly use *separate* accounts per flow rather than netting everything into one. Acted on: the single settlement account was split into `NgnInboundSettlementAccount` and `NgnOutboundSettlementAccount`, two `wallets` rows under the same reserved customer ID with distinct account types — no schema change needed beyond seeding the second row, since `(customer_id, currency, account_type)` uniqueness already supported it. The AI's original single-account design wasn't wrong for what it needed to do, but I had real settlement/treasury context it didn't, and it hadn't proposed the better model until directly prompted — a reminder that some gaps aren't "the AI made a mistake," they're "the AI never had the domain context to know there was a better option."

**`idempotency_keys` has no retention policy.** `IdempotencyStore.CompleteAsync` updates a claimed row in place and never deletes it — every successfully completed transfer or external-outbound request leaves a permanent row, and nothing documented a retention policy. I distinguished this from the actual ledger tables (`transactions`/`audit_log`/`transaction_reversals`, which must be kept forever): `idempotency_keys` only protects against a near-term retry, so a bounded TTL (24–72 hours) pruned by a scheduled job would be correct. **Deliberately not implemented** — I asked for it to be documented rather than built, since for a project at this scale, showing the gap and its fix is understood matters more than shipping every operational concern. Recorded in the README as a named limitation. Worth including specifically to show the *decision not to fix* was reasoned, not silently skipped.

## What this suggests about directing AI on a project like this

None of these were caught by "does this look right" review of the generated code — each looked reasonable on inspection. I caught them three ways:

1. A design conversation that insisted the AI justify trade-offs, or that I steer toward a stated future requirement, rather than accepting the first plausible answer that satisfies today's acceptance criteria.
2. Tests that assert exact, aggregate outcomes rather than only "did the request succeed."
3. Actually reading the structured logs/exception a failure carries before assuming the bug is in whatever was most recently written.

For a financial ledger, the concurrency bug is the one that matters most — a concurrency-safety claim is only as good as the test that tries hardest to break it. The wallet-cardinality decision matters most for this being a component inside a larger product — "correct for the brief" and "correct for where the product is going" are different bars, and the second one needed me to name the future requirement out loud, not the model to infer it.
